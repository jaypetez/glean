# v1.3 Migration Guide

v1.3 follows the v1.2 security audit with reliability, end-to-end testing, agent-friendliness, and documentation/branding work. There are no intentional breaking changes to `feeds.yaml`, but operators should run the checks below after upgrading.

## What changed since v1.2

- **Security audit:** v1.2 completed a 17-PR hardening pass covering API key handling, SSRF defenses, prompt-injection defenses, secret scrubbing, file/sink validation, HTTP hardening, container hardening, and SQLite safety settings.
- **E2E + agent friendliness:** v1.3 added seven PRs focused on migration safety, DST regressions, property/API fuzzing, E2E stability, Makefile/pre-commit developer workflow, trace IDs, richer health output, and agent instructions.
- **Branding and docs foundation:** the adjacent docs initiative added the logo suite, branded UI/docs surfaces, README screenshots, MkDocs Material navigation, generated references, and strict docs builds.

## Required actions

### 1. Run state migrations

PR #139 introduced yoyo-managed SQLite migrations. They run automatically when the app opens the state store, but after upgrading you should also run them explicitly once:

```bash
docker exec -it glean glean migrate --db /data/state.db
```

For non-Docker installs, point `--db` at your configured `GLEAN_DB` path.

### 2. Keep API auth enabled in production

Verify `GLEAN_DISABLE_AUTH` is not set in production `.env`, Compose files, systemd units, or reverse-proxy environments:

```bash
grep -R "GLEAN_DISABLE_AUTH" .env docker-compose.yml
```

`GLEAN_DISABLE_AUTH=1` is only for local test harnesses or trusted loopback-only deployments with another authentication layer in front of glean.

### 3. Check `/data` permissions

The bind-mounted data directory contains the SQLite database and API key verifier. Make it private to the container operator:

```bash
chmod 700 /data
chmod 600 /data/api_key  # if the verifier already exists
```

If you mount `./data` from the host, apply equivalent permissions to that host directory before starting the container.

### 4. Review file sink paths

The #94 path allowlist work constrains file sink writes to `/data` or `/tmp/glean` by default. If any feed writes outside those roots, move the output under an allowed root or set `GLEAN_FILE_SINK_ROOTS` deliberately.

```yaml
sinks:
  - type: file
    path: /data/digests/ai-news.jsonl
    format: jsonl
```

For custom roots:

```env
GLEAN_FILE_SINK_ROOTS=/data,/archive
```

Make sure each root exists, is writable by the glean process, and is not broader than needed.

## Recommended validation

After the required checks, run a dry run before resuming scheduled sends:

```bash
docker exec -it glean glean validate-config
docker exec -it glean glean test-feed <feed-name>
docker compose logs -f glean
```

Watch the first scheduled run after upgrade for migration messages, auth warnings, path validation errors, and any unexpected sink failures.
